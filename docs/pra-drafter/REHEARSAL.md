# PRA Drafter - rehearsal report (2026-09-26)

Owner's rule: green unit tests are not proof. This is the record of an
adversarial end-to-end rehearsal against a local build (`npm run build &&
npx next start -p 3107`), stub model provider only (`PRA_MODEL_STUB=1`),
local Postgres (`postgres://localhost/fincrime_dev`), no real client data,
no prod DB, no push.

## What was run

- **Rehearsal register**: `test/fixtures/drafter-rehearsal/register-rehearsal.xlsx`
  (generated by `scripts/gen-rehearsal-register.mjs`) - 76 data rows:
  52 realistic rows spread across CDD/EDD/Sanctions/Transaction
  Monitoring/Correspondent Banking, 8 jurisdictions, both customer types,
  and Yes/Partial/No/blank coverage; every SPEC.md import-validation case
  (missing columns, formula error, placeholder tag value, contradiction,
  duplicate REQ ID, empty draft input, translation==original); plus 15
  marker rows carrying the writer/judge/tagger stub trigger tokens through
  the real pipeline (not just DB-inserted for unit tests).
- **Rehearsal stub file**: `test/fixtures/drafter-rehearsal/rehearsal-stub.json`
  (`scripts/gen-rehearsal-stub.mjs`) - extends the existing
  `test/fixtures/drafter/writer-stub.json` with writer/judge cases for
  invented numbers/frequencies/roles/system names, banned phrases, REQ ID
  in control text, em dash, over-length text, malformed JSON, judge
  pass/minor/critical/quote-not-found/unknown-criterion/malformed, and new
  tagger cases: good tags, tags mixing valid values with invented
  out-of-list values, and malformed tagger JSON.
- **Browser walkthrough**: `scripts/qa-walkthrough.mjs`, a real Playwright
  script (not curl) driving Chromium against the built app: anonymous and
  non-allowlisted personas, then the allowlisted first-time journey
  (documents -> template extraction -> StylePack -> register import ->
  validation/override -> library/tagging -> start PRA -> draft all ->
  judge all -> approve+promote -> export blocked -> export override ->
  real .docx downloaded), then mobile (390px), 1920 and 3840x1080 viewport
  checks.
- **Sessions**: minted directly via `scripts/mint-rehearsal-sessions.mjs`
  (same `sessions`/`users` tables the app itself uses - no shortcut around
  `requireDrafterActorApi`).
- **Export inspection**: the downloaded `.docx` was unzipped
  (`word/document.xml`, `word/styles.xml`) and converted to PDF with
  LibreOffice (`soffice --headless --convert-to pdf`) and the rendered
  pages were viewed.

## Issue list (found -> fixed)

1. **[FIXED] Register import: resolved/overridden blocking issues looked identical to unresolved ones.**
   `components/drafter/DrafterRegisterDetailClient.tsx` kept rendering live
   "Mark resolved"/"Override" buttons for every blocking issue regardless
   of whether it had already been resolved (the server correctly cleared
   `is_blocked`, but the per-issue UI never reflected it). Confirmed live:
   scripted automation clicking "the first Override button" 4 times in a
   row overrode the **same row 4 times**, writing 4 duplicate audit-log
   rows, before the real target rows were ever reached. Fix: added
   `listValidationOversForVersion`-style batched query
   (`listValidationOverridesForVersion` in `lib/repo/drafter-register.ts`),
   returned as `overridesByRow` from `GET /api/drafter/register/[importId]`,
   and the client now renders a "Resolved by <actor>" / "Overridden by
   <actor>" badge (with the logged reason) in place of the buttons once a
   check has a resolution. Verified live after the fix: the API returns
   `overridesByRow` correctly keyed, and re-running the full override
   sequence produced exactly one override per blocking row, no duplicates.

2. **[FIXED - most important finding] "Draft all remaining" silently
   abandoned the rest of the batch on the first per-enhancement failure.**
   `DrafterPraDraftClient.tsx`'s `draftAllRemaining()` used `break` on the
   first failed draft call (e.g. one bad/malformed model response) and
   showed only a transient error message. Confirmed live: with one
   deliberately-malformed marker row present, every enhancement queued
   *after* it in processing order was left completely un-drafted (no
   control text, no error, indistinguishable from "not yet clicked") even
   though the "Draft all remaining" button had finished and re-enabled
   itself - a reviewer would reasonably believe every selected control had
   been drafted. Fix: the loop now continues past a failure, collects every
   failure, and shows a persistent summary ("Drafted N of M. K failed - see
   the red 'Model error' line on each affected enhancement below") instead
   of silently stopping. Verified live after the fix: with the same
   malformed marker present, all 9 marker enhancements plus every other
   pending enhancement were drafted in one pass; only the genuinely-broken
   one stayed undrafted, with its inline error visible.

3. **[FIXED - from code review] Unbounded direct-upload finalize path.**
   `app/api/drafter/documents/route.ts`'s directUpload finalize handler
   read an entire Blob-hosted file into memory with no byte cap, and the
   upload-token route (`app/api/drafter/documents/upload-token/route.ts`)
   issued tokens with no `maximumSizeInBytes`, so a multi-GB or zip-bomb
   .xlsx/.docx could exhaust the function's memory. Fix: `MAX_DIRECT_UPLOAD_BYTES`
   (50MB) passed as `maximumSizeInBytes` on token issuance, and a new
   `readStreamBounded()` helper (`lib/drafter/bounded-stream.ts`) that
   aborts the read the moment the running total exceeds the same 50MB cap
   on the finalize side, returning a 413 with a clear message. Unit tested
   (`lib/drafter/__tests__/bounded-stream.test.ts`, 4 cases: under cap,
   over cap mid-stream, exactly at cap, empty stream). Residual limitation:
   this bounds the *compressed* upload size, not the fully-decompressed
   xlsx/docx content a zip bomb could inflate to - `exceljs`/`mammoth` do
   not expose a decompressed-size ceiling, so a small-but-malicious file
   within the 50MB cap could still expand significantly during parsing.
   Not fixed this pass; flagged for a future hardening pass if this module
   is ever opened to less-trusted uploaders.

## Minor observations (not fixed - working as designed or out of scope)

- The "Standard" home-page copy ("Skeleton extraction ... is a later phase
  of this build") reads like an internal engineering note rather than
  end-user copy. Harmless (module is allowlist-only, all viewers are
  already engineering-literate here) but worth rewording in a future pass.
- A rehearsal register built entirely of "coverage: Yes, no agreed wording"
  rows produces a long unbroken run of `[Agreed wording not held for this
  control]` placeholders in the exported document - correct behaviour
  (never fabricates reused wording) but worth knowing a real register with
  more agreed wording pre-populated will look very different.
- Re-running "New StylePack (seeded)" / template extraction with no guard
  against duplicates creates multiple StylePack/template versions if
  clicked twice; not a data-integrity issue (versioned by design) but no
  UI warning is shown.

## Follow-up round (same day) - close-out items

The owner asked for five more things to be closed before calling this
ready, all done against the same local build/stub/DB, no push:

4. **Zip-bomb guard.** `lib/drafter/zip-guard.ts`'s `guardZipBounds()`
   opens the zip's central directory only (via `jszip`'s `loadAsync`,
   which reads entry metadata without inflating any entry) and rejects
   over 10,000 entries or 200MB of *declared* uncompressed size, before
   ExcelJS/mammoth ever see the bytes. Wired into both the multipart and
   direct-upload finalize paths in `app/api/drafter/documents/route.ts`
   for `.docx`/`.xlsx` only. Tested
   (`lib/drafter/__tests__/zip-guard.test.ts`, 5 cases) including a
   **crafted high-ratio zip bomb**: a single 210MB-of-repeated-`"A"` entry
   that compresses to under 1MB - confirmed compressed size, then
   confirmed the guard rejects it - plus a real fixture `.docx`/`.xlsx`
   passing, an entry-count bomb, and a non-zip file. Residual limit noted
   in the original issue list stands (bounds declared size, not a nested/
   recursive zip-of-zips, which mammoth/ExcelJS do not support anyway).

5. **Second PRA reuse, walked on screen.** Started a second PRA
   ("Correspondent Banking Reuse Check") after approving `RQJPASSMK` in
   the first PRA. Verified on the candidate-selection screen: the
   `RQJPASSMK` control now shows "used in Correspondent Banking" (product
   name) and no longer shows "no agreed wording held yet, will draft as a
   placeholder". Selected it, confirmed, drafted: the second PRA's
   enhancement text is **byte-identical** to the first PRA's approved
   wording (confirmed in Postgres - two `drafter_enhancements` rows for
   `RQJPASSMK` share the exact same `control_text`). The on-page text
   assertion in the walkthrough script itself had a timing/dump quirk (a
   short wait wasn't quite enough before the dump) - the database check is
   the authoritative proof and passed.

6. **Calibration run to a decision, on screen, both directions.**
   Imported a deliberately mislabelled item (`JUDGE-PASS` marker text
   labelled "fail" on all 6 criteria against a stub that returns all-pass)
   and ran it: **0% overall agreement, "failed threshold"** shown in Run
   history, and the PRA page's "Reviewer not yet calibrated" banner was
   confirmed still present. Cleared the set, imported the same text
   correctly labelled "pass" on all 6 criteria, ran it: **100% overall
   agreement, "passed threshold"**, and the banner was confirmed **gone**
   from the PRA page immediately after. Both directions proven on the real
   calibration screen against `GET /api/drafter/calibration/status`.

7. **Double-submit guards.** Added a synchronous `useRef` lock (not just
   the existing `busy`/`drafting` React state, which only takes effect on
   the next render and therefore does not close a same-tick double-click)
   to every create-style action that had none or an incomplete one:
   `createStylepack`, `extract`, `createAndConfirm`
   (`DrafterTemplatesClient.tsx`), `startPra` (`DrafterPrasListClient.tsx`,
   previously had `busy` state but no ref lock), and `submitCandidates`
   (`DrafterPraDraftClient.tsx`, previously had **no** in-flight guard at
   all - confirmed as a real, if minor, gap). Verified live: two `.click()`
   calls dispatched on the *same DOM button* in the same synchronous tick
   (a true double-click, not two separate Playwright action calls, which
   have their own async pipeline and are not equivalent) now fire exactly
   **one** `POST /api/drafter/stylepacks`, not two. (Along the way, an a11y
   label fix below briefly regressed the walkthrough script itself - see
   note.)

8. **Accessibility basics.** Every unlabelled input/select found was
   fixed: the candidate-control checkboxes (`aria-label` per control,
   wrapped in `<label>`), the manual-gap description input and section
   `<select>` (wrapped in `<label>` with `sr-only` text), and the document
   upload `<input type="file">` (wrapped in `<label>` with `sr-only`
   text). The library's filter tabs got `aria-pressed` plus a `font-semibold`
   weight change so the selected state is not colour-only. Status markers
   (`Badge`) already carry text, not just colour, so no change was needed
   there. Global `:focus-visible` styling already exists site-wide
   (`app/globals.css`), giving every native control (all buttons here are
   real `<button>` elements) a visible focus ring for free - verified the
   "Run judge" button is reachable by keyboard Tab from page load; did not
   exhaustively tab through every conditionally-revealed control (e.g.
   "Apply fix" only appears after a judge run is triggered and a criterion
   fails, so a blind Tab-from-load pass does not reach it - this is
   correct hide-until-relevant behaviour, not a bug, since it is a real
   `<button>` once rendered). **Self-caught regression**: the first version
   of the file-upload label's `sr-only` text ("Choose a file to **upload**")
   accidentally gave the native file-picker its own accessible name
   matching `/upload/i`, which made the walkthrough's
   `getByRole("button", {name: /upload/i})` pick the wrong element and
   silently open a file dialog instead of submitting the form. Fixed by
   rewording the label; a lesson for any future accessible-name work here
   is to check it doesn't collide with another interactive element's name
   on the same screen.

## What remains unproven

- The real Vercel Blob client-direct upload path for a file genuinely over
  4MB (no `BLOB_READ_WRITE_TOKEN` in this local environment - matches
  HANDOFF-4's own note). Explicitly out of scope for this pass per the
  owner - to be proven on the deployed app instead.
- The zip-bomb guard bounds *declared* uncompressed size and entry count
  from the central directory; it does not defend against a maliciously
  corrupted central directory that under-reports size (ExcelJS/mammoth
  would still need to actually parse such a file to discover the
  mismatch, at which point the 50MB compressed-upload cap is still the
  backstop).
- Screen-reader software (VoiceOver/NVDA) was not run - accessibility
  checks were DOM-role/keyboard/contrast-adjacent only (labels present,
  `aria-pressed`, focus-visible, colour-independent status text, Tab
  reachability of one representative always-visible control). Full
  assistive-technology testing of the drafter module remains unproven.
- Double-submit guards were verified live on one representative button
  (`New StylePack`); the other four buttons share the identical ref-lock
  pattern but were not each individually double-click-tested.
